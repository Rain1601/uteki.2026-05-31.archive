# 面试讲述 · Uteki 项目 · 3-5 min + 8-10 min 双版本

> **场景**：基金面试官说"详细讲讲这个项目"（最常见的开场题）
> **目标**：3 分钟让面试官产生具体追问的兴趣；8 分钟让他相信你既懂投资又懂工程
> **本文档不是写出来读的，是脚本**——口语化、有停顿、有节奏

---

## 0. 演讲设计的 4 个底层原则

1. **3 件深 > 5 件浅** —— 8 分钟讲 3 个设计决策每个 2 分钟，胜过讲 5 个每个 1 分 30 秒。**讲少能讲深的人，比讲多浅的人显得更可信**
2. **从"个人痛点"起手不从"技术先进性"起手** —— 基金人 allergic to "我用了 SOTA 框架"，但喜欢 "我遇到一个真实问题"
3. **必须有一个数字** —— 任何讲述如果听完连一个量化指标都没留下，叙事失败
4. **必须有一句"我没做好的事"** —— 主动承认 weakness 比避而不谈强 5 倍，特别是基金文化（桥水的 radical transparency 直接是这个）

## 1. 三个必讲的设计选择（分析 + 怎么讲）

### 🥇 设计 A · 7-Gate 投资框架 codify
**为什么必讲**：唯一能同时证明"懂投资框架"和"懂如何把心法变成代码"。其他工程候选人没有这条。

**怎么讲（30-90 秒版本）**：
> "我把 Fisher 的 15 问、Buffett 的护城河、Munger 的反向测试这套**传统价值投资框架**，拆成了 7 个序贯的 gate。每个 gate 是一个独立 LLM 调用，强制输出结构化 JSON —— 不是自由文本，是 Pydantic schema。下一个 gate 必须**基于上一个的结论 + 引用源 ID** 来推理。
>
> 这样做的好处是 —— 我不是让 LLM "随便分析一下"，我是让它**按照成熟投资人的思考顺序走一遍**，每一步都可被人审视。"

**Killer detail（如果有时间）**：
> "Gate 3 是护城河，Gate 5 是 Munger 反向测试 ——'什么情况下我会错'。我特意在 Gate 3 和 Gate 5 后面插了 **Reflection Checkpoint**：检测前后 gate 是否矛盾，如果 Gate 1 说"高增长"但 Gate 3 说"营收下滑"，矛盾会被抓出来注入后续 gate。"

**讲完后留的追问钩子**：
- "为什么 7 个不是 5 个或 10 个？" → 答：这是投资框架本身的结构，不是技术决策
- "Gate 间怎么传递？" → 答：摘要 vs 全文双模式

---

### 🥇 设计 B · `as_of` 时间窗 + Provenance + 引用强制
**为什么必讲**：基金面试官听到这 3 个词，**60 秒内会判断你是否真的懂回测可信度**。错过这 60 秒你的可信度就到顶了。

**怎么讲（60-90 秒版本）**：
> "做 LLM 投资 agent 最容易'作弊'的一件事是 —— **回测的时候用了未来数据**。比如你回测 2023 年 1 月买不买 Apple，结果 LLM 用了 yfinance 的实时接口，把 2024 年的财报数据偷偷喂进去了，回测胜率自然好看。
>
> 我做了三层防御：
> 第一层，每个工具调用回来的数据点都注册到一个 `SourceCatalog`，带着 **source / url / published_at** 元数据。
> 第二层，LLM 输出强制带 `[src:1,3]` 这种引用标记，没有引用的论断会被 parser 拒绝。
> 第三层，回测时传一个 `as_of` 时间戳，catalog 会**主动拒绝任何 published_at 晚于 as_of 的数据点**，并记到日志。
>
> 这套机制不是 nice-to-have，是这个 agent 能不能上线的前提。"

**Killer detail（如果有时间）**：
> "yfinance 用 `history(end=as_of)` 切片；FMP 按 quarterly filing date 过滤；SEC EDGAR 用 filing 时间戳；新闻类源按 publication_date 严格切片。"

**讲完后留的追问钩子**：
- "你怎么确保所有工具都遵守这个？" → 答：所有 tool 通过 catalog 统一入栈，无 bypass
- "你能复现 6 个月前的某次决策吗？" → 顺势接到下一个话题

---

### 🥈 设计 C（选一个）

#### C1 · ConsistencyRunner（**千象 / quant 方向选这个**）
**怎么讲**：
> "LLM 不可解释 —— 这是基金人最大的顾虑。我的回答不是'让 LLM 变可解释'，而是'让 LLM 的**输出稳定性变可测量**'。
>
> 我做了一个 ConsistencyRunner —— 同一个标的输入，mock 掉外部工具，跑 N=10 次相同的 7-Gate pipeline，然后量化：
> - 最终 action（买/持/卖）的一致率
> - 每个 gate 输出的 score CV（变异系数）
> - 跨 run 的 categorical agreement
>
> 这样我能告诉自己'这个 prompt 在这个标的上**有多稳**'，超过阈值就降级到人工审核。"

**讲完留的钩子**：
- "CV 阈值你设多少？" → 答：根据 gate 类别不同，估值 gate 容忍 0.15，护城河 gate 容忍 0.25
- "如果 mock 工具，怎么知道在真实环境也稳？" → 答：mock 是测 LLM 内在不稳定，真实环境另跑一组对比

#### C2 · Arena 3-phase（**桥水方向选这个**）
**怎么讲**：
> "投资决策最危险的一种情况是 —— **单一模型的偏见被当成真理**。我建了一个 Arena 评测：
> Phase 1，让 7 个不同 LLM 独立给同一个标的的判断。
> Phase 2，每个 LLM 看其他模型的输出（去 model name 匿名化），按"逻辑一致性 / 引用充分性 / 结论合理性"投 approve 或 reject。
> Phase 3，按 adoption / rejection / win count 累计每个模型的分。
>
> 本质上这是 Bridgewater 说的 **idea meritocracy** 的工程化 —— 不预设哪个模型权威，让 idea 自己竞争。"

**讲完留的钩子**：
- "怎么避免投票偏向自己？" → 答：去 model name + 评判维度固定 + 多次 random shuffle
- "vote 阶段的 prompt 怎么写？" → 准备好答案

## 2. 3-5 分钟版本（精简）

### 结构（总长 4 分钟 ≈ 600 字）

```
[20s] 钩子 + 一句话定位
[30s] 个人触发：投资的真实痛点
[40s] uteki 是什么：scope + 工程概况
[120s] 三件最重要的事（A + B + C），每个 40s
[20s] 一个数字（consistency 或 cost）
[15s] 一个反思：还没做到什么
[15s] 邀请追问
```

### 完整脚本（4 分钟版，照读即可）

> **[钩子 - 20 秒]**
> 用 LLM 做投资决策，最难的事**不是让它给答案**，而是**让它给的答案可被信任、可被复现、可被审计**。我个人项目 uteki 就是在 4 个月里把这件事系统化地推到了能用的程度。
>
> **[触发 - 30 秒]**
> 项目起因是我自己投美股的真实痛点 —— 看一份财报要花一晚上，看完还经常漏掉关键风险。我尝试过让 ChatGPT 帮我分析，但**每次回答都不一样、引用的数据时不时是错的、复现不出来**。所以我决定不是去找一个更好的 prompt，而是**搭一套有约束的 pipeline**。
>
> **[scope - 40 秒]**
> uteki 是 4 个月单人主导的个人项目，218 个 commit，覆盖**美股 / 港股 / A 股**。后端 FastAPI + PostgreSQL，前端 React，集成了 OpenAI / Anthropic / DeepSeek / Qwen 等 7 家 LLM Provider。但**架构层面真正有价值的是三件事**：
>
> **[设计 A - 40 秒]**
> 第一件，**把 Fisher 15 问、Buffett 护城河、Munger 反向测试**这些价值投资框架拆成 7 个序贯的 gate。每个 gate 强制输出结构化 JSON，下游 gate 必须基于上游的结论和引用源 ID 推理。这不是让 LLM"随便分析"，是让它**按成熟投资人的思考顺序走一遍**。
>
> **[设计 B - 40 秒]**
> 第二件，**回测无未来数据泄漏**。LLM agent 回测最容易作弊的就是用了未来数据。我做了 SourceCatalog —— 每个数据点带 published_at，回测时传 as_of 时间戳，catalog 会**主动拒绝任何晚于 as_of 的数据**。LLM 输出还强制带 `[src:N]` 引用，没引用就拒收。
>
> **[设计 C - 40 秒]**
> 第三件，**量化 LLM 输出稳定性**。LLM 不可解释这事我绕开 —— 我做 ConsistencyRunner，同输入跑 10 次，量化 action 一致率和 gate score CV。超阈值就降级人工。我能告诉你"**这个 prompt 在这个标的上有多稳**"，而不是凭感觉。
>
> **[数字 + 反思 - 20 秒]**
> 当前在 [GOOGL / AAPL / 等] 上测得 action 一致率 XX%、单次完整分析 token 成本 X.XX 美元。**还没做到的一件事**是 —— 历史 5 年回测的真实超额收益数据。我接下来会跑出来。
>
> **[邀请 - 15 秒]**
> 哪一块您想深入聊？我可以从架构层面、决策可信度层面、或者具体某个 gate 的设计逻辑展开。
```

### 4 分钟版的"必须留住的 3 句话"
1. "**用 LLM 做投资决策，最难的不是让它给答案，是让它给的答案可被信任**"
2. "**回测最容易作弊的就是用了未来数据**"
3. "**LLM 不可解释这事我绕开 —— 我让它的输出稳定性可被衡量**"

## 3. 8-10 分钟版本（深度）

### 结构（总长 9 分钟 ≈ 1300 字）

```
[30s]  钩子 + 一句话定位
[60s]  背景：当前用 LLM 投资的 3 个普遍问题
[60s]  uteki 是什么：scope + 触发 + 单人交付
[120s] 设计 A（7-Gate codify）含 Reflection Checkpoint
[150s] 设计 B（as_of + Provenance）含 3 层防御
[120s] 设计 C（ConsistencyRunner 或 Arena）
[60s]  一个真实的工程教训（缓存污染或类似）
[45s]  量化结果 + 现在的局限
[30s]  邀请追问
```

### 完整脚本（9 分钟版）

> **[钩子 - 30 秒]**
> 用 LLM 做投资决策，最难的事不是让它给答案，是**让它给的答案可被信任、可被复现、可被审计**。这正好和基金的核心需求是同一个 —— 你们要的是 systematic、reproducible、auditable 的决策过程。我个人项目 uteki 用 4 个月把这套基础设施推到了能用的程度，**虽然出发点是 C 端但实际架构更适合 B 端**。
>
> **[背景 - 60 秒]**
> 我观察现在用 LLM 做投资 agent 的项目，普遍有三个问题：
> **一**、回答不稳定 —— 同一个问题问 10 次，10 个答案。
> **二**、回测作弊 —— LLM 看到了未来的数据，自然回测好看。
> **三**、决策不可追溯 —— 当用户问"你为什么 6 个月前让我买这个"，没人答得上来。
>
> 我做这个项目的认知是：**单纯优化 prompt 解决不了这三个问题，必须从架构层面解决。**
>
> **[scope + 触发 - 60 秒]**
> uteki 是 4 个月单人主导的个人项目，218 个 commit，覆盖美 / 港 / A 股。后端 FastAPI + PostgreSQL，前端 React + TypeScript，集成 7 家 LLM Provider。架构上有 12 个 domain。但**真正有价值的是 3 个核心设计决策**，我详细讲一下。
>
> **[设计 A - 120 秒]**
> 第一个决策是把**投资框架本身**编码进 pipeline。我把 Fisher 的 15 问、Buffett 的护城河评估、Munger 的反向测试这些经典框架，拆成了 7 个序贯的 gate：
>
> - Gate 1-2 业务理解
> - Gate 3 护城河
> - Gate 4 管理层
> - Gate 5 Munger 反向测试 —— 也就是"什么情况下我会错"
> - Gate 6 估值
> - Gate 7 Synthesis
>
> 每个 gate 强制输出 Pydantic 定义的结构化 JSON —— 结论 + 置信度 + 引用源 ID。下游 gate 必须**基于上游的引用**来推理。
>
> 我特意在 Gate 3 和 Gate 5 之后加了 **Reflection Checkpoint** —— 检测前后 gate 是否矛盾，比如 Gate 1 说"高增长"但 Gate 3 说"营收下滑"，矛盾会被自动抓出来，修正信号注入到后续所有 gate。
>
> 这套设计的本质是：**我不让 LLM 自由发挥，我让它按照成熟投资人的思考顺序走一遍，每一步都可审视、可中断、可修正。**
>
> **[设计 B - 150 秒]**
> 第二个决策是**回测可信度工程**。LLM agent 回测最容易作弊的事 —— 用了未来数据。比如你回测 2023 年 1 月买不买 Apple，但 yfinance 的实时接口偷偷把 2024 年的财报数据喂进去，回测胜率自然好看。
>
> 我做了三层防御。
>
> **第一层**，自建 SourceCatalog —— 每个 tool 调用回来的数据点都带元数据：source、url、published_at。
>
> **第二层**，LLM 输出强制带 `[src:1,3]` 这种引用标记，parser 检查每个引用对应到 catalog 里真实存在的数据点。没引用的论断会被拒收。
>
> **第三层**，回测时传一个 `as_of` 时间戳到 RunContext，catalog 会**主动拒绝任何 published_at 晚于 as_of 的数据点**，并记 warning 日志。
>
> 具体到工具层面 —— yfinance 用 `history(end=as_of)` 切片，FMP 按 quarterly filing date 过滤，SEC EDGAR 用 filing 时间戳，新闻类源按 publication_date 严格切片。
>
> 这套机制不是 nice-to-have，是这个 agent 能不能上 production 的前提。
>
> 顺便提一下 —— 因为整个 pipeline 的事件流（每次 LLM I/O、每个 tool call、每个 gate 中间结论）都持久化到 PG，所以**给定一个 decision_id，可以逐 token 重放 6 个月前的决策**。这对基金的合规审计是有用的。
>
> **[设计 C - 120 秒，这里 quant 选 ConsistencyRunner / 桥水选 Arena]**
>
> *如果对方是 quant：*
> 第三个决策是**量化 LLM 输出稳定性**。LLM 不可解释这件事我不试图解决，我绕开 —— 我让它的稳定性可被衡量。
>
> 具体做法：ConsistencyRunner —— 同一个标的输入，mock 掉外部工具确保数据一致，然后跑 N=10 次相同的 7-Gate pipeline。聚合三类指标：
> - 最终 action（买/持/卖）的 mode 一致率
> - 每个 gate 输出的 score CV（变异系数）
> - categorical 字段的 mode agreement
>
> 超过阈值的标的（比如 CV > 0.25）就自动降级到人工审核，不让模型决策。
>
> 这是把 statistical evaluation 的语言搬到 LLM agent 上 —— 不是"我相信模型说的"，是"我能告诉你**这个 prompt 在这个标的上的输出有多稳**"。
>
> *如果对方是桥水：*
> 第三个决策是 Arena 3-phase 多模型评测，本质是 idea meritocracy 的工程化。
>
> Phase 1，让 7 个不同 LLM 独立判断同一个标的（不互相看）。
> Phase 2，每个 LLM 看其他模型的输出（model name 匿名化），按"逻辑一致性 / 引用充分性 / 结论合理性"投 approve 或 reject + reasoning。
> Phase 3，按 adoption / rejection / win count 累计每个模型的分，形成 model leaderboard。
>
> 整个流程**每个 model 用独立 DB session**（避免并发冲突），**pipeline_state 字段记录阶段**（支持断点续跑）。
>
> 本质思路是：**不预设哪个模型权威，让 idea 通过结构化评审收敛共识**。哪个模型在哪类问题上更可靠，是数据回答的，不是人拍脑袋。
>
> **[工程教训 - 60 秒]**
> 讲一个我踩过的真实坑 —— 有一次用户分析 Tesla，返回的报告内容**完全是 Microsoft 的业务模型和财务数据**。原因是 gate 级缓存 key 没包含 symbol，不同股票的同一个 gate 共享了缓存。诡异的是 Gate 7（synthesis）不走缓存所以最终格式正确，但内容基于错误的前置 gate。这个 bug 在 production 跑了 3 天才被用户发现 —— 因为 **LLM 输出"看起来合理"，但完全是错的**。
>
> 教训：LLM 系统里的缓存比传统 cache 危险 10 倍。错误命中不会报错，只会输出"看起来合理但根本错"的内容。从那以后我所有 cache key 强制包含上下文标识，并加了 self-consistency 检查。
>
> **[数字 + 局限 - 45 秒]**
> 量化结果：当前在 [GOOGL / AAPL / etc.] 测得 N=10 次重跑 action 一致率 XX%，gate score CV XX%，单次完整分析 token 成本 X.XX 美元。
>
> 我**最大的硬伤是 —— 还没有真实的多年回测 alpha 数据**。我有这个系统能保证回测无未来信息泄漏，但还没系统地跑 5 年 10 个标的的实证。这是我接下来 1-2 周要补的，因为没有这个数字，前面所有的工程价值都不够说服力。
>
> **[邀请 - 30 秒]**
> 我刚才主要讲了三个设计选择 —— 投资框架 codify、回测可信度、稳定性量化。哪一块您想深入聊？或者您更想了解我接下来怎么做实证、或者这套架构怎么扩展到 multi-strategy ensemble？

### 9 分钟版的"必须留住的 5 个关键信号"

1. ✅ "**4 个月、218 commit、单人交付**" → 完成度信号
2. ✅ "**Fisher / Buffett / Munger 的框架 codify**" → 懂投资的信号
3. ✅ "**as_of + Provenance 三层防御**" → 懂回测的信号
4. ✅ "**TSLA 返回 MSFT 数据的 bug 故事**" → 工程深度 + 自省信号
5. ✅ "**最大硬伤是还没真实回测 alpha**" → 诚实信号

少任何一条，整段都会失色。

## 4. 通用演讲技巧（任何版本都适用）

### 4.1 该停顿的 5 个地方
1. **钩子最后一句之后** —— 留 2 秒让面试官接收
2. **"3 件事"宣告之后** —— "**真正有价值的是三件事**【1 秒停】我详细讲一下"
3. **每个设计开始前**：宣告 + 停顿 —— "**第一件事 / 第二件事**【0.5 秒停】"
4. **数字之前** —— "我测得【0.5 秒停】action 一致率 XX%"
5. **承认硬伤前** —— "**我最大的硬伤是【1 秒停】还没有真实的多年回测 alpha 数据**"

### 4.2 该重读 / 加重的 7 个词
- "**可被信任**" 
- "**可被复现**"  
- "**可被审计**"
- "**作弊**"（指 lookahead bias）
- "**主动拒绝**"（指 as_of 防御）
- "**单人**"
- "**4 个月**"

### 4.3 该避免的 6 种讲法
- ❌ "我用了 Multi-Agent 框架……" → 改 "我把投资框架 codify 成了 pipeline"
- ❌ "这里用到了 ReAct / CoT / RAG……" → 用业务语言替换
- ❌ "我觉得 LLM 很有潜力……" → 太空，立刻具体到一个问题
- ❌ "比 LangChain / AutoGen 更好……" → 不要主动比较框架
- ❌ "其实这个项目还有……" → 不要塞 4-5 个次要点，让追问带出
- ❌ "我也用了一些 SOTA 的东西……" → buzzword，扣分

### 4.4 钩子 / 结尾的 3 个模板（任选一个）

**钩子模板**：
- A：「用 LLM 做投资决策，最难的不是让它给答案，是让它给的答案可被信任。」← 推荐
- B：「我做 uteki 的时候发现，传统价值投资人和 LLM agent 之间隔着一个'决策可被审计'的鸿沟。」
- C：「我 4 个月做了一件事 —— 把 Fisher / Buffett / Munger 的投资框架 codify 成可量化稳定性的 LLM 决策 pipeline。」

**结尾模板**：
- A：「哪一块您想深入聊？」← 最简洁，推荐
- B：「我也想反过来问 —— 您团队当前在 LLM + 投资这块的最大挑战是什么？」← 高级，但需要面试官状态对的时候才用
- C：「这是我从这个项目里学到的最大一件事 —— **Agent 工程不是 prompt engineering，是 decision credibility engineering**。」← 哲学升华，留印象深

## 5. 面试官可能的"打断 + 追问"应对

讲到一半被打断追问是好事，说明对方真在听。常见 5 类追问：

### 5.1 "为什么 7 个 gate"
→ 答：投资框架本身的结构（Fisher / Buffett / Munger 三家共 6 维度 + 1 综合）。不是技术拍脑袋。

### 5.2 "你的 LLM 用的哪家"
→ 答：默认 DeepSeek + OpenAI 兼容协议。曾经支持 7 家 Provider，但**这不是项目重点**，重点是 7-Gate 框架 + 可信度工程。**主动把话题拉回来**。

### 5.3 "你的回测 Sharpe 多少"
→ 当前你的硬伤。诚实答：「这是我接下来 1-2 周要补的关键数据。我已经有跑回测的基础设施（`backtest_collect.py`），但 5 年系统化数据还没完整跑出来。」然后补一句：「**正因为我有 as_of 时间窗约束，跑出来的数字才会是诚实的**。」

### 5.4 "你和 LangChain / AutoGen 比有什么优势"
→ 不要正面对比框架。答：「我没用现成框架是因为我需要的是**对投资决策可信度的精确控制** —— provenance、as_of 强制、cross-gate 一致性 —— 这些在通用 agent 框架里要绕弯。自建大约 2k 行代码换来完全可控的执行流。」

### 5.5 "这个项目你打算继续做吗"
→ 诚实答：核心架构资产已经迁到 uteki（next-gen）。uteki.open 完成了它的使命 —— 把所有难点踩了一遍。**这个回答比"我会继续维护"更显得专业**。
